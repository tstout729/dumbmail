# Cloudbeds recipe

Checked against Cloudbeds' documentation on 2026-11-18; not yet run against a live account.

- **Webhooks.** Subscribed one action at a time with `POST /api/v1.3/postWebhook` (`object`, `action`, `endpointUrl`, optional `authHeaderName` and `authHeaderValue`). Deliveries are JSON POSTs; "order of the events is not guaranteed"; a failed delivery is retried after a minute, up to five attempts; `timestamp` is the original event time in Unix seconds. Ids are spelled `reservationID` in some events and `reservationId` in others, and the recipe reads both. Source: [Webhooks](https://developers.cloudbeds.com/docs/webhooks-1).
- **Authentication.** "Cloudbeds does not sign payloads" (their `timestamp` isn't signed either, and isn't used): the supported way to authenticate deliveries is the header given as `authHeaderName`/`authHeaderValue` when subscribing. The recipe checks `X-Webhook-Token` (constant-time). There's no timestamp to check, so there's no signature window; a webhook only names a reservation, and what's recorded always comes from fetching it. Source: [Webhooks](https://developers.cloudbeds.com/docs/webhooks-1).
- **Events used.** `reservation/created`, `reservation/status_changed`, `reservation/dates_changed` (and the accommodation changes, if subscribed) fetch the reservation. `reservation/deleted` marks the reservation object deleted and not paid, as of when DumbMail handles the webhook, because a deleted reservation can't be fetched. That's later than every request for it sent before then, so none of their answers can bring it back; only a later answer in which Cloudbeds returns it again does (a deleted one comes back as `success: false`, which writes nothing). Other events (`notes_changed`, guest events) are ignored. Source: [Webhooks](https://developers.cloudbeds.com/docs/webhooks-1).
- **The reservation.** `GET /api/v1.3/getReservation?reservationID=…` with an `x-api-key` header (scope `read:reservation`): `status` (`confirmed`, `not_confirmed`, `canceled`, `checked_in`, `checked_out`, `no_show`), `guestEmail` (the main guest), `guestList` (entries with `isMainGuest`, names and phones), `startDate`, `endDate`, `total`, `balance`, `balanceDetailed` (`grandTotal`, `paid`), `dateCreated`, `dateModified`, `dateCancelledUTC`, `isAnonymized`, `assigned`/`unassigned` (adults, children). Source: [getReservation](https://developers.cloudbeds.com/reference/get_getreservation-2).
- **Paid in full.** Cloudbeds has no "paid" flag. getReservation "includes balance (pending payment) and paid (amount already paid)". Paid in full means: a booked status, `total` above zero, `balanceDetailed.grandTotal` present and equal to it, `balance` exactly zero, and `balanceDetailed.paid` equal to the total, all compared exactly as decimals (no floating point; a JSON number or plain decimal text). Anything missing or inexact means not paid. The answer's `reservationID` must be the one asked for. Sources: [getReservation](https://developers.cloudbeds.com/reference/get_getreservation-2), [Reservation FAQs](https://developers.cloudbeds.com/docs/reservation-faqs).
- **Payments.** A payment changes a reservation's balance but sends no reservation webhook. Cloudbeds reports money it has taken as posted transactions (`accounting/transaction`), which this recipe doesn't read, so it records no revenue. getReservations warns that "some reservations modification may not be reflected" in `dateModified`. So every hour the pull lists confirmed arrivals (`GET /api/v1.3/getReservations?status=confirmed&checkInFrom=…&checkInTo=…`, 100 a page, the documented maximum) from yesterday to `payment_check_days` ahead, and fetches each one again. Source: [getReservations](https://developers.cloudbeds.com/reference/get_getreservations-2).
- **Versions.** Each fetched reservation is written to its own `cloudbeds_reservation` object (external id `cloudbeds:<id>`; not Guesty's `reservation` type, so flows built for other booking systems never act on it) with `as_of` and `paid_checked_at` set to when DumbMail sent the request (`input.request.sent_at`). A later request for the same reservation is only sent once an earlier answer is stored, so an answer to an earlier request (a retry, a slow run) never overwrites a later one. Every field is written each time; one the answer doesn't give is cleared, never left from before.
- **Events.** Cloudbeds Reservation Confirmed (once per reservation, when first seen confirmed, checked in or checked out), Cloudbeds Reservation Cancelled (once, dated by `dateCancelledUTC`), Cloudbeds Checked Out (once). Their own names, so they never start flows built on Guesty's or Hostaway's events; no money and no purchase marker. A guest whose data was anonymized gets no profile and no events.
- **No starter flow.** The recipe ships no pre-arrival email: it couldn't fail closed on the payment evidence Cloudbeds documents.
- **Consent.** Cloudbeds has no marketing opt-in field. Guests are held back from marketing; relay addresses (Booking.com, Expedia and others) are suppressed by the framework.

## Removed before anything is stored

The recipe keeps only what it reads (an allow-list): from webhooks the event, ids, status and timestamp; from getReservation the id, property, status, main guest's email, names and phones, dates, money totals and room occupancy counts. Guest documents, birthdates, tax ids, addresses, cards on file, custom fields (which may hold door or gate codes), notes and guest requirements are dropped. The list also names the reservation object's own fields (`check_in`, `paid_in_full` and so on), because an integration's allow-list applies to the object fields it writes too.

## What a live check should look at first

- The exact format of `dateModified`, `dateCreated` and `dateCancelledUTC` (ISO 8601 or `YYYY-MM-DD HH:MM:SS`, and in which zone).
- Whether `balance`, `balanceDetailed.paid` and `grandTotal` are numbers or text, and that a fully paid reservation shows `balance: 0` and `paid` and `grandTotal` equal to `total`.
- What getReservation answers for a deleted reservation (`success: false` is assumed).
- Whether `checkInFrom`/`checkInTo` take plain dates as documented, and that `pageSize=100` is accepted.
- That a `postWebhook` subscription with `authHeaderName`/`authHeaderValue` really sends the header on deliveries.
- Whether getReservation needs `propertyID` for keys that cover several properties.
