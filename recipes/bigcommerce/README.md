# BigCommerce recipe

Checked against BigCommerce's documentation on 2026-11-17; not yet run against a live store.

- **Thin webhooks.** A callback is `{"scope", "store_id", "data": {"type", "id", …}, "hash", "created_at", "producer": "stores/<store_hash>"}`; "the `data` object for `store/order/statusUpdated` contains only the order `id`", and BigCommerce says to fetch the order next. So each webhook's script asks DumbMail to fetch the record (`next_request`) with the store's API token, and runs again on the answer. Sources: [Webhooks](https://docs.bigcommerce.com/docs/integrations/webhooks) and [Webhook events](https://docs.bigcommerce.com/developer/docs/integrations/webhooks/event-reference/events).
- **Authenticity.** BigCommerce doesn't sign callbacks; a webhook is created with a `headers` object that BigCommerce sends with every callback "so that webhook destination URIs can be secured". The recipe checks a secret token in `X-Webhook-Token`, and ignores callbacks whose `producer` is another store. Source: Webhooks → Security.
- **Signature window.** BigCommerce doesn't sign callbacks or send a timestamp; the secret header is checked on every request, a callback with the same `hash` within 10 minutes is a resend, and every event's id comes from BigCommerce's ids. Source: [Webhooks](https://docs.bigcommerce.com/docs/integrations/webhooks).
- **Duplicates.** BigCommerce says callbacks can arrive more than once and suggests the `hash` to spot them. The `hash` is of the payload data, which is the same for two different updates of one order, so it isn't used as a message id; instead every event has a `unique_id` from BigCommerce's ids, and each fetch reads the order's current state.
- **Orders.** `GET /stores/{store_hash}/v2/orders/{id}` (header `X-Auth-Token`). An order is paid when its `payment_status` is `captured`, `paid`, `partially refunded` or `refunded`; `authorized`, `pending`, `capture pending`, `held for review`, `declined`, `void`, `additional action required` and empty aren't, whatever the fulfilment status says. Fulfilled Order on status 2 (Shipped) or 10 (Completed), Cancelled Order on 5. Dates are RFC 2822 in UTC. Sources: [Get Order](https://docs.bigcommerce.com/developer/api-reference/rest/admin/management/orders/get-order), [Get Order Statuses](https://docs.bigcommerce.com/developer/api-reference/rest/admin/management/orders/order-status/get-order-statuses).
- **Money.** `total_inc_tax`, with `default_currency_code` ("the transactional currency the shopper pays in") on each event. An order with a total of 0 isn't counted.
- **Refunds.** `GET /v3/orders/{order_id}/payment_actions/refunds/{refund_id}` gives `order_id`, `created`, `reason` and `payments[]` (`amount`, `is_declined`). BigCommerce notes a refund id resolves even under another order, so the refund counts only when its `order_id` is the order the webhook named, and only its payments that BigCommerce marks `is_declined: false` count toward its amount (a payment without the flag isn't proof the money moved). The order is then fetched for the buyer and currency, and the refund recorded once by its id. Source: [Get Order Refund](https://docs.bigcommerce.com/developer/api-reference/rest/admin/management/order-operations/payment-actions/get-order-refund-by-id).
- **Customers.** `GET /v3/customers?id:in=<id>`. `accepts_product_review_abandoned_cart_emails` is about review and abandoned-cart emails, not a marketing opt-in, so it isn't used. Source: [Get Customers](https://docs.bigcommerce.com/developer/api-reference/rest/admin/management/customers/v3/get-customers).
- **Consent.** The order's `is_email_opt_in` "indicates whether the shopper has selected an opt-in check box (on the checkout page) to receive emails". BigCommerce doesn't say the box is unticked by default or that it's about marketing, so it subscribes nobody unless the installer sets `checkout_opt_in_is_marketing` to `true` (off by default), confirming the store's box starts unticked and clearly asks for marketing email. Then the billing email of a shopper who ticked it is subscribed with that source; otherwise everyone stays held back from marketing.
- **Import.** `GET /v2/orders` with `min_date_modified` (inclusive), `sort=date_modified:asc`, `limit` and `page`. A short or empty page ends a run: the cursor moves to the newest change read and paging starts over from page 1 (an empty page after an exactly full one doesn't leave it stuck). Source: [Get All Orders](https://docs.bigcommerce.com/developer/api-reference/rest/admin/management/orders/get-orders).

## Removed before anything is stored

IP addresses, order and customer notes, `customer_message`, checkout `form_fields` (shoppers type delivery instructions and gate codes there), card type, payment provider ids and `authentication`, at any depth.

## What a live check should look at first

- Which currency `total_inc_tax` is in when the shopper pays in a currency other than the store's default.
- That `GET /v2/orders` answers 204 with an empty body when nothing changed (the script treats it as no orders).
- How quickly an order can be read after `store/order/created` (a 404 is retried).
